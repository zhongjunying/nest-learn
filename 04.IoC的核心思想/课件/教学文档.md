## 为什么需要 IoC —— 从三层架构说起

前面学过三层架构与 MVC，在后端体系中，代码通常分为以下几个层次：

- **Controller（控制器）**：接收请求、返回响应
- **Service（服务）**：处理业务逻辑
- **Dao / Repository（数据访问对象）**：对数据库执行增删改查
- **DataSource（数据源）**：根据配置连接和管理数据库

这些层次之间存在明确的依赖关系：Controller 依赖 Service，Service 依赖 Dao，Dao 依赖 DataSource。按照传统的写法，你需要**手动按顺序创建**每一层的实例：

```typescript
const dataSource = new DataSource(config);
const dao = new Dao(dataSource);
const service = new Service(dao);
const controller = new Controller(service);
```

在真实项目中，业务模块非常多，不同的 Controller 可能调用**同一个 Service**。如果每次都 `new` 一个新的 Service，就会产生多个不同的实例，违背了**单例模式**的原则——我们希望整个应用中，同一个 Service 只有**一个实例**，所有 Controller 共享它。

手动管理这种依赖关系和单例，在大型应用中是极其繁琐且容易出错的。**IoC（控制反转）** 正是用来解决这个问题的。

## IoC 与 DI 的概念

**IoC（Inverse of Control，控制反转）** 是一种设计思想：将对象的创建和依赖管理的控制权，从程序代码转移到外部容器中。

**DI（Dependency Injection，依赖注入）** 是 IoC 的具体实现方式：由外部容器将所需的依赖对象"注入"到目标对象中，而不是由目标对象自己创建依赖。

> IoC 是"干什么"的思想，DI 是"怎么干"的具体手段。

具体来说，IoC 容器在应用初始化时，会做以下几件事：

1. **扫描**应用中各个类上声明的依赖关系
2. **按顺序创建**相应实例，并放入容器中统一管理
3. **自动提供**——当某个类需要使用依赖时，直接从容器中取出注入

这样，开发者**不再手动 `new` 对象**，而是声明"我需要什么"，由容器来提供。

## 餐厅后厨比喻：看懂控制反转

如果你觉得概念抽象，可以想想去餐厅吃饭的过程：

- **传统做饭**：你自己买菜、洗菜、切菜、掌握火候、炒菜、洗碗——一切由你主动控制
- **去餐厅就餐**：你告诉服务员"来一份红烧牛肉盖浇饭"，剩下的全部交给后厨处理

在这个比喻中：

| 现实场景 | IoC 中的对应 |
|---------|------------|
| 后厨 | IoC 容器 |
| 菜单（上面写了需要哪些食材） | 类上声明的依赖 |
| 服务员把菜单传给后厨 | 依赖注入的过程 |
| 后厨根据菜单准备好饭菜端上来 | 容器创建好实例并提供给需要的类 |

**从主动下厨到等待服务员上菜，这就是控制反转的精髓。**

## 传统方式 vs IoC 方式

下面用一个**电商订单系统**来对比两种写法。系统中有三个服务：

- `PaymentService` —— 处理支付
- `ShippingService` —— 处理发货
- `OrderService` —— 创建订单，依赖前两个服务

### 传统方式：主动创建依赖

在 `OrderService` 的构造函数中，直接 `new` 出它需要的依赖：

```typescript
class PaymentService {
  processPayment(amount) {
    console.log(`处理付款金额: $${amount}`);
    return true; // 假设支付成功
  }
}

class ShippingService {
  shipOrder(orderDetails) {
    console.log(`订单发货至: ${orderDetails.address}`);
  }
}

class OrderService {
  constructor() {
    // 直接在构造函数中创建依赖
    this.paymentService = new PaymentService();
    this.shippingService = new ShippingService();
  }

  createOrder(amount, address) {
    console.log(`创建订单金额： $${amount}`);
    const paymentSuccess = this.paymentService.processPayment(amount);

    if (paymentSuccess) {
      console.log(`订单创建成功!`);
      this.shippingService.shipOrder({ address });
    } else {
      console.log(`付款失败。订单创建已中止!`);
    }
  }
}

// 直接创建 OrderService 的实例
const orderService1 = new OrderService();
orderService1.createOrder(200, '成都市天府三街');
```

### IoC 方式：被动等待注入

先实现一个简易的 IoC 容器：

```typescript
class Container {
  constructor() {
    this.services = new Map(); // 存储服务实例
  }

  // 注册服务到容器中
  register(name, service) {
    this.services.set(name, service);
  }

  // 获取服务实例
  get(name) {
    const service = this.services.get(name);
    if (!service) {
      throw new Error(`Service ${name} not found!`);
    }
    // 如果服务是一个工厂函数，执行它来创建实例
    if (typeof service === 'function') {
      const instance = service(this);
      this.services.set(name, instance); // 实例创建后缓存起来
      return instance;
    }
    return service;
  }
}
```

然后，让 `OrderService` 不再自己创建依赖，而是通过构造函数参数接收：

```typescript
class PaymentService {
  processPayment(amount) {
    console.log(`处理付款金额: $${amount}`);
    return true;
  }
}

class ShippingService {
  shipOrder(orderDetails) {
    console.log(`订单发货至: ${orderDetails.address}`);
  }
}

class OrderService {
  constructor(paymentService, shippingService) {
    // 依赖由外部传入，而不是自己 new
    this.paymentService = paymentService;
    this.shippingService = shippingService;
  }

  createOrder(amount, address) {
    console.log(`创建订单金额：$${amount}`);
    const paymentSuccess = this.paymentService.processPayment(amount);
    if (paymentSuccess) {
      console.log(`订单创建成功!`);
      this.shippingService.shipOrder({ address });
    } else {
      console.log(`付款失败。订单创建已中止!`);
    }
  }
}

// 创建一个 IoC 容器实例
const container = new Container();

// 先将各个服务注册到容器中
container.register('paymentService', new PaymentService());
container.register('shippingService', new ShippingService());

// orderService 的注册使用工厂函数，容器会在需要时创建并缓存
container.register('orderService', (container) => {
  return new OrderService(
    container.get('paymentService'),
    container.get('shippingService')
  );
});

// 从容器中获取 OrderService
const orderService1 = container.get('orderService');
orderService1.createOrder(200, '成都市天府三街');
```

> 两种方式最终执行效果完全一致，但**控制权发生了变化**：传统方式是 `OrderService` 自己 `new` 依赖，IoC 方式是将依赖的创建交给容器管理，`OrderService` 只负责接收和使用。

## 单例管理：IoC 的关键优势

传统方式下，每次获取订单服务都可能无意间创建新实例：

```typescript
const orderService1 = new OrderService();
const orderService2 = new OrderService();

console.log(orderService1 === orderService2); // false
console.log(orderService1.paymentService === orderService2.paymentService); // false
```

两个 `orderService` 是不相等的，它们内部的 `paymentService` 也是不同的对象。这意味着每个 Service 都有自己的状态，无法共享资源（比如数据库连接池、缓存状态）。

IoC 模式下，由于容器会缓存已创建的实例，多次获取得到的是同一个对象：

```typescript
const orderService1 = container.get('orderService');
const orderService2 = container.get('orderService');

console.log(orderService1 === orderService2); // true
console.log(orderService1.paymentService === orderService2.paymentService); // true
```

这就是 IoC 容器的**单例管理**能力。只要注册时使用工厂函数（如上面代码所示），容器在第一次调用 `get` 时创建实例并存入 `Map`，后续再次 `get` 直接返回缓存结果。

## 动手验证：传统模式和 IoC 模式的差异

项目中的 Demo 代码在 `04.IoC的核心思想/代码/test-ioc/` 目录下，分别对应两个文件：

- `test1.js` —— 传统模式，每次 `new` 都是新对象
- `test2.js` —— IoC 模式，容器保证单例

### 运行传统模式

```bash
node "04.IoC的核心思想/代码/test-ioc/test1.js"
```

输出结果类似：

```
创建订单金额： $200
处理付款金额: $200
订单创建成功!
订单发货至: 成都市天府三街
false   ← orderService1 === orderService2
false   ← orderService1.paymentService === orderService2.paymentService
```

### 运行 IoC 模式

```bash
node "04.IoC的核心思想/代码/test-ioc/test2.js"
```

输出结果类似：

```
创建订单金额：$200
处理付款金额: $200
订单创建成功!
订单发货至: 成都市天府三街
true    ← orderService1 === orderService2
true    ← orderService1.paymentService === orderService2.paymentService
```

两个文件最终的订单创建效果相同，但最后的 `true / false` 对比结果截然不同——这正是 IoC 容器带来的单例管理能力的体现。
